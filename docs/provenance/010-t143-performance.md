# Spec 010 T143 — Performance and Stress Qualification

Status: CANDIDATE

## Canonical authority

- Canonical predecessor: T142A guarded merge `8d75cab455f11afddeaa6fbe6244dbb1021d1467`.
- The T142A merge tree is `0b5a601b8103aa23e8b30a6169308afdde1a9241` and all 11 workflows triggered by that merge completed successfully.
- T143 is authorized by the accepted Spec 010 task order. T144 remains blocked until T143 is `CLOSED_CANONICAL`.

## Purpose

T143 qualifies the final pre-Founder-review desktop shell against the frozen launch, interaction, render, idle-resource, large-scale, output, and resize budgets. It measures before optimizing. No performance framework, WebGL path, virtualization layer, renderer package, or runtime dependency is added by this task.

## Measurement boundary

The reference performance environment is the exact GitHub `ubuntu-24.04` runner used by the `t143-performance` workflow. Evidence records the runner image identity, exact candidate/tree, toolchain versions, WebKitGTK package/runtime version, browser host, release binary hash, renderer-dist hash, fixture identity, raw samples, and threshold disposition.

Native launch and idle-resource measurements use the release Tauri host plus its descendant WebKitGTK processes. The benchmark-only build feature adds a page-load observation hook but no Tauri command, IPC authority, dependency, persistence path, network service, or production behavior. The renderer marks a populated two-Session fixture shell ready after two animation-frame boundaries, then performs a same-origin benchmark marker navigation observed by the host hook.

Renderer interaction measurements use WebKitGTK automation through `WebKitWebDriver` and GNOME Web/Epiphany in automation mode. The browser host is a measurement harness for the same WebKitGTK engine; it does not substitute for the native Tauri cold-launch/idle measurements.

## Required campaigns

The exact-head workflow retains raw/lossless-enough results for:

- at least 20 native cold launches with p95 `<= 1500 ms`;
- at least 1000 exact Session-selection samples with p95 `<= 50 ms`;
- at least 1000 composer keystroke-to-paint samples with p95 `<= 16 ms`;
- at least 1000 single/dual layout transitions with p95 `<= 100 ms`;
- at least 1000 local right-dock tab switches with p95 `<= 50 ms`;
- at least 1000 divider resize samples under two visible representative Session work streams;
- a `>=100 Project / >=1000 Session` fixture with measured search, scroll, and focus behavior;
- 60 seconds of native Tauri/WebKitGTK idle CPU/RSS sampling with CPU `<=2%` of one logical core and renderer+host RSS `<=300 MiB`;
- inherited exact-candidate live output stress processing at least 10 MiB and 100,000 logical lines while preserving terminal lifecycle/ownership plus 1000 backend resize operations;
- deterministic hidden-output batching across multiple simulated sessions proving bytes are coalesced before renderer writes rather than scheduling one full-frame action per byte.

## Non-authority and nonclaim boundaries

The composer timing harness temporarily enables the fixture textarea in the measurement DOM only. It never submits a prompt, calls a runtime/provider, or changes canonical T139 composer availability. This is a paint-overhead measurement, not runtime-input evidence.

The large fixture exists only in `VITE_WINDS_T143_BENCHMARK=1` builds. Production builds retain the canonical/fixture bridge choice established before T143. The production Tauri command count remains 22 and the standard security/authority workflows remain authoritative.

No T143 result may be used as cross-platform performance equivalence. T142 remains the direct platform-coverage authority; T143 performance ceilings are qualified on the declared Ubuntu/WebKitGTK reference environment.

## Qualification-discovered workflow regression repair

The first exact-head T143 candidate (`d40053bcf3ccd54e4ea20d761f27c7ce13a48447`) exposed a repository-owned CI defect before qualification could close: the already-closed `t142a-winds-identity` workflow compared every later desktop PR against the current PR base/head and re-applied the historical T142A implementation allowlist. It therefore rejected T143's separately authorized workflow, Tauri benchmark feature/hook, and T143 provenance paths before running the intended T142A regression checks.

T143 repairs that stale gate without weakening the accepted T142A boundary. The workflow now re-verifies the immutable canonical T142A base/head/merge parentage, tree identity, and original path allowlist, then runs the Current Spectrum deterministic regression gates against the current candidate. It no longer treats T142A's historical implementation scope as the authority model for later canonically authorized tasks. The failed first run remains historical evidence and is not rerun-to-green on the stale candidate.

## Independent-review repair

The first independent exact-head review of successor `6e4744afae775a63eea091f196d9f6d74b62b2d8` found one material harness gap: the 60-second idle CPU/RSS campaign recorded process counts and names but did not require a WebKit renderer to remain present, so a host-only remainder could theoretically satisfy the frozen `renderer+host` resource ceilings. That reviewed head is therefore not qualification authority.

The first live campaign after that repair, on successor `6fb4a1d75a2410e1a3ecf05ddf53866f5049ca48`, failed the unchanged `renderer+host idle RSS <=300 MiB` gate with an aggregate process-tree RSS maximum of `420.891 MiB`; launch, idle CPU, renderer-presence, and process-count checks passed. That failure is retained as real diagnostic evidence and is not rerun-to-green. The next successor adds per-process RSS attribution only; it does not change the RSS scope, threshold, sample duration, or pass/fail calculation.

The attribution successor `a31cf38dd8dcb5a8addf8ecfbcf74ae3ea481ac2` also failed the unchanged aggregate RSS gate (`425.402 MiB`) while proving the peak split was host `161.359 MiB`, WebKit web renderer `204.629 MiB`, and WebKit network process `59.414 MiB`; launch p95 (`1375.2275 ms`), idle CPU (`0.51548%`), renderer-presence, and process-count gates passed. The measured renderer pressure justifies a forward-only product optimization: keep the canonically accepted Terminal sub-surface selected in workbench mode, but defer loading/allocating xterm.js until the user explicitly starts a Rust-owned terminal. Terminal selection, Rust lifecycle/authority, command count, security behavior, and the frozen performance thresholds remain unchanged.

The resulting product successor `d1e83cfa0805041a94ea64e21bc73ce335efc519` preserved every non-T143 workflow and passed independent exact-head review with zero material findings, but its exact-head T143 campaign still failed: aggregate RSS was `412.918 MiB` (host `152.258 MiB`, WebKit renderer `201.172 MiB`, network `59.488 MiB` at the peak), and cold-launch p95 was `1637.966 ms`; idle CPU remained `0.46551%`. The xterm deferral therefore remains a valid product optimization but is insufficient for T143 closure. A further Linux product optimization disables JavaScriptCore JIT before WebKitGTK initialization, using WebKit's supported `JSC_useJIT=false` runtime option. The same setting is applied to the WebKitGTK renderer campaign so the measured reference environment matches the shipped Linux runtime profile. No threshold, metric, sample floor, authority surface, or non-Linux runtime behavior is changed.

The JIT-bounded successor `15db16eff0364cda69dadeef83464fc32edf4b97` passed all three exact-head static reviews with zero material findings and restored cold-launch qualification (`1365.1684 ms` p95) while lowering idle CPU to `0.39918%` and aggregate RSS to `387.285 MiB` (host `150.469 MiB`, WebKit renderer `177.910 MiB`, network `59.078 MiB`). The unchanged RSS gate still failed, so that head is retained as diagnostic evidence and is not qualification authority. The next forward-only Linux product optimization also sets Tauri's documented WebKitGTK `WEBKIT_DISABLE_COMPOSITING_MODE=1` before WebView creation, and the WebKitGTK renderer harness receives the same setting. Winds does not use WebGL or accelerated canvas as an authorized product surface; all frozen renderer interaction budgets remain active, and final T144 visual review remains mandatory, so this change cannot qualify by memory reduction alone if it harms responsiveness or presentation.

The compositing-disabled successor `0c047e828059abf29bca7095b2b38ef481411400` also failed the unchanged RSS gate at `390.156 MiB` (host `152.973 MiB`, WebKit renderer `178.344 MiB`, network `58.969 MiB`) while cold launch (`1062.969 ms` p95) and idle CPU (`0.58162%`) passed. The compositing switch therefore produced no measured memory benefit and is removed in the next forward-only successor rather than retained speculatively.

Four measured RSS failures separately justified the narrow dependency experiment contemplated by T143 acceptance. The `e2ec318df068fc0869edd965affabac6a07aa2fd` successor exposed the already-locked transitive `webkit2gtk = 2.0.2` crate as a Linux-only direct host dependency and applied WebKitGTK's `DocumentViewer` cache model to the existing Winds WebContext. Its exact-head campaign still failed the unchanged RSS gate at `394.414 MiB` (host `157.215 MiB`, WebKit renderer `178.316 MiB`, network `59.098 MiB`) while cold launch (`1062.7369 ms` p95) passed. The cache-model/direct-dependency experiment therefore produced no measured memory benefit and is fully removed in the next forward-only successor.

The next dependency-neutral successor retains the previously measured JIT-off improvement and enables JavaScriptCore's normal `libpasScavengeContinuously` option before the first VM. JavaScriptCore documents `JSC_<option>` environment overrides as the supported pre-VM configuration path and defines `libpasScavengeContinuously` specifically to keep the libpas allocator scavenging continuously. The same option is inherited by the native WebKit process tree and explicitly applied to the WebKitGTK renderer campaign. CPU and interaction ceilings remain unchanged, so allocator reclamation cannot qualify by RSS reduction if it consumes excessive CPU or harms responsiveness.

That allocator successor `c30535fd3a399911abd71522792c90e3fa4ecc20` falsified the hypothesis decisively: cold-launch p95 regressed to `2012.7792 ms`, idle CPU rose to `299.12266%` of one logical core, and aggregate process-tree RSS remained `400.703 MiB` (host `156.617 MiB`, WebKit renderer `178.445 MiB`, network `65.641 MiB`). The allocator override is therefore removed completely in the next successor rather than retained speculatively.

The same failed campaign exposed two measurement-seam defects that are repaired without changing any frozen budget. First, native readiness had been signaled by a benchmark-only renderer navigation to `t143-ready=1`, causing a full WebKit reload after the shell was already useful and making the idle sample include measurement-induced navigation/page-cache state. The successor replaces that with an X11 window-title sentinel set after the same two `requestAnimationFrame` boundaries; no reload, new Tauri command, host feature, or IPC seam is required. The normal release Tauri host is built with a deterministic two-Session native qualification renderer, preserved byte-for-byte for evidence, and only then is the separate renderer-only benchmark/scale fixture built for the WebKit interaction campaigns.

Second, the frozen Plan/Tasks wording is `renderer+host idle RSS <=300 MiB`, not aggregate host+renderer+network-process RSS. The successor therefore gates the literal Tauri host plus WebKit rendering descendants, while continuing to retain WebKit network-process RSS and the entire process-tree RSS in every raw sample as diagnostics. A WebKit renderer remains required in every sample, and the host-plus-renderer gate is not replaced by PSS, unique memory, a raised threshold, or a reduced sample duration.

The forward-only successor requires every retained idle sample to include at least one descendant process whose Linux `comm` contains `WebKit`, requires at least two processes (host plus descendant) in every idle sample, records per-sample names and renderer-presence truth, and includes both predicates in the native checks propagated into combined `all_checks_pass`. This closes the review finding without changing the product command surface or performance ceilings.

## Closure discipline

T143 may close only after the complete exact-head candidate passes deterministic gates, the T143 performance workflow, all other applicable workflows, author correctness/safety review, Ponytail/YAGNI review, fresh independent substantive review with zero material findings, zero unresolved review threads, guarded expected-head merge, verified merge parentage/tree/signature, and every workflow actually triggered by the merge commit.

T143 closure authorizes T144 only. It does not create or substitute the human Founder visual acceptance required by T144.

The `137c9527a27189181ad885dee02fd90efc5373a8` successor removed the fixture/canonical dock-binding failure, proving the deterministic Session fixtures can reach the native host without stale canonical right-dock calls. It then exposed a second readiness-seam defect: changing `document.title` does not propagate to the native Tauri window title on the Ubuntu/WebKitGTK host, so the external X11 harness could not observe the already-rendered useful shell. The next successor preserves the same renderer readiness predicates and two animation-frame boundary, but uses the existing Tauri core window API to set the native title. The permission is supplied only through an inline `TAURI_CONFIG` capability on the qualification build and grants exactly `core:window:allow-set-title` to the `main` window. Production `tauri.conf.json` remains `capabilities: []`; no capability file, custom Rust command, IPC endpoint, dependency, or shipped renderer authority is added.

The exact-head `754612ed6da5f562bb1acbc073521d824d31f698` campaign finally reached the undistorted native measurement boundary. Cold launch (`1079.8336 ms` p95), idle CPU (`0.59849%` of one logical core), renderer presence, and process-count gates passed. The literal frozen host+renderer RSS gate remained the sole failure at approximately `330 MiB` (host `150.8 MiB`, renderer `179.2 MiB`), while the diagnostic full process tree was `388.996 MiB` including the network process. The next successor therefore tests one dependency-neutral Linux product hypothesis only: WebKit's documented `Malloc=1` switch, which disables WebKit bmalloc/libpas allocation in favor of the system allocator. The shipped Linux host sets it before WebKit initialization and the separate WebKitGTK renderer campaign receives the same profile. The 300 MiB RSS ceiling, launch/CPU/interaction budgets, sample floors, authority surface, dependencies, and non-Linux behavior remain unchanged. This allocator profile is experimental until exact-head measurement proves benefit; failure requires forward-only removal rather than threshold relaxation.

The allocator successor `e30dcc4922a7aeeed76f970ba1c268e343dddb53` retained successful launch (`1083.2407 ms` p95), idle CPU (`0.61455%`), renderer-presence, and process-count checks while lowering the literal host+renderer RSS peak from about `330 MiB` to `316.523 MiB` (host `146.582 MiB`, renderer `169.941 MiB`; network `47.266 MiB` diagnostic). `Malloc=1` therefore has measured benefit and is retained, but the unchanged `300 MiB` gate still fails by about `16.5 MiB`.

Fresh exact-head review then identified four qualification-integrity defects that must be repaired before any T143 result can qualify: the closed T142A regression workflow must require the current candidate to descend from the canonical T142A merge; native host output capture must not be able to fill a pipe and stall the measured process; Linux descendant discovery must enumerate children of every thread; and the WebDriver HTTP/script timeouts must be long enough for the frozen 5000-sample normal renderer campaign. The successor repairs all four without changing a performance threshold, sample floor, product authority surface, or measurement scope.

Because `Malloc=1` now routes WebKit allocation through the system allocator, the same measured failure separately justifies one further dependency-neutral Linux allocator experiment: set `MALLOC_ARENA_MAX=1` before WebKit child processes start. glibc documents that additional arenas trade higher memory usage for lower allocation contention. The exact-head campaign must therefore prove both RSS improvement and preservation of every launch, CPU, and interaction ceiling; otherwise this arena limit is removed forward-only.

The exact-head `a0a230914ea9600e993acb6382a0d341e8bc01c0` arena-bounded campaign retained launch (`1053.3014 ms` p95), idle CPU (`0.56453%`), renderer presence, and process-count gates, but host+renderer RSS remained above the frozen ceiling at `315.191 MiB` (host `145.965 MiB`, renderer `169.227 MiB`). `MALLOC_ARENA_MAX=1` yielded only a small additional measured reduction from the preceding `316.523 MiB` and caused no observed regression. The next forward-only Linux allocator experiment keeps the measured `Malloc=1` and arena bound and sets glibc `MALLOC_TRIM_THRESHOLD_=0` before WebKit initialization so freed top-of-heap pages are aggressively returned to the operating system in the host and inherited WebKit processes. The frozen RSS, launch, CPU, interaction, sample-floor, security, and authority requirements remain unchanged; the trim override is retained only if exact-head measurement proves benefit without regression.

The exact-head `36b2863fa25cf1c276be54402dfce06d254988f9` trim-threshold campaign again passed launch (`1056.1992 ms` p95), idle CPU (`0.51473%`), renderer-presence, and process-count gates, but host+renderer RSS was still `314.137 MiB` (host `145.699 MiB`, renderer `168.711 MiB`; network `47.109 MiB` diagnostic). The aggressive glibc trim setting improved the arena-bounded result by only about `1.054 MiB`, so it is removed rather than accumulated as a weak product override. Successor `11cf26bd0f89c92828e488e01f24e6fa4f94683b` initially proposed JavaScriptCore's `JSC_forceRAMSize=8589934592` option, but author correctness review rejected that product profile before performance qualification because a fixed reported RAM size could overstate physical memory on a lower-memory Linux machine. No performance claim is taken from that superseded head. The corrected successor keeps only the measured-beneficial `JSC_useJIT=false`, `Malloc=1`, and non-regressing arena bound, and instead raises JavaScriptCore's supported pre-VM `JSC_aggressiveHeapThresholdInMB` to `1048576` (1 TiB). JavaScriptCore continues to observe the machine's real RAM for heap sizing, but ordinary desktop/workstation systems stay on the default rather than aggressive heap-growth mode. This changes neither OS memory limits nor the T143 RSS ceiling, measurement scope, sample floors, security authority, or non-Linux behavior. Exact-head CI must prove both memory benefit and preservation of every launch, CPU, and interaction ceiling.

The exact-head `a566396e22939ddecd7506564583d548a7bba42d` default-growth experiment passed launch (`1055.8005 ms` p95), idle CPU (`0.53195%`), renderer-presence, and process-count checks but regressed host+renderer RSS to `315.723 MiB` (host `145.922 MiB`, renderer `169.801 MiB`; network `47.234 MiB` diagnostic). `JSC_aggressiveHeapThresholdInMB` is therefore removed. That result also confirms the remaining gap is not materially explained by JSC's aggressive heap-growth mode. The next successor removes the qualification-only `WEBKIT_DISABLE_DMABUF_RENDERER=1` override from both native and renderer harnesses. The override is not a Winds product default and forces WebKitGTK away from its default DMABUF renderer onto a fallback path; retaining it would make the frozen reference measurement less representative of the production WebView. `GDK_BACKEND=x11` and all T143 thresholds, scopes, sample floors, security boundaries, and readiness semantics remain unchanged. Exact-head CI must prove that the default renderer is viable under the pinned Ubuntu/Xvfb reference environment and must satisfy the same memory and performance ceilings; otherwise the experiment is rejected.

The exact-head `8d72a4de722ecc4853cdd3928791c922f11fb683` default-DMABUF experiment falsified that hypothesis under the pinned Ubuntu/Xvfb reference environment. Cold launch remained within budget at `1331.0628 ms` p95, but idle CPU rose to `7.20094%` of one logical core and literal host+renderer RSS rose to `515.746 MiB` (host `184.465 MiB`, renderer `336.156 MiB`; network `47.164 MiB` diagnostic). The reference harness therefore restores `WEBKIT_DISABLE_DMABUF_RENDERER=1`; it is an Xvfb qualification compatibility setting, not a Winds product default, and the failed exact-head evidence is retained rather than rerun.

Repeated measured RSS failures now justify a narrower product-side WebKit configuration through the already-locked `webkit2gtk = 2.0.2` crate. The successor exposes that existing transitive crate as a Linux-only direct host dependency without introducing or changing any locked third-party package. After Tauri creates the existing main WebView, Winds disables WebGL, WebAudio, WebRTC, accelerated 2D canvas acceleration, and the WebKit page cache because none is an authorized or implemented Winds desktop surface. JavaScript, DOM/CSS rendering, the terminal lifecycle, and every frozen T143 interaction/visual requirement remain active. The workflow proves the only lockfile change is the root `winds-desktop-host` dependency reference and keeps every RSS, launch, CPU, interaction, sample-floor, security, and authority ceiling unchanged. Exact-head measurement decides whether this configuration is retained.

The exact-head `3b1d692d690bbb8e615d7de84c2333320564478e` unused-WebKit-surface experiment also failed to improve the frozen RSS gate. Cold launch and idle CPU remained within budget, with idle CPU falling to `0.34984%`, but host+renderer RSS was `315.414 MiB` (host `146.062 MiB`, renderer `169.352 MiB`; network `47.172 MiB` diagnostic). Because the direct `webkit2gtk` reference and post-creation feature toggles produced no material RSS benefit, they are removed completely in the next successor; the desktop host returns to the prior dependency graph.

With `Malloc=1` already proving that WebKit allocation can be routed through glibc, the next successor tests one allocator-cache mechanism only: when `GLIBC_TUNABLES` is otherwise unset, set `glibc.malloc.tcache_count=0` before WebKit initialization so WebKit descendants do not retain glibc per-thread tcache freelists. GNU libc documents that a zero `glibc.malloc.tcache_count` disables the per-thread cache. Author review caught an important qualification seam before this successor was committed: exporting `GLIBC_TUNABLES` (and the other product allocator/JSC settings) globally from the native harness would apply them to the Tauri host at process startup even though the shipped executable can set them only from `main()` before WebKit initialization. The corrected native campaign therefore starts the host without those harness-only exports and relies on the shipped Rust profile for WebKit descendants; only the separate WebKitWebDriver renderer campaign receives the equivalent environment at its own process launch. The pinned Xvfb reference still keeps its required `WEBKIT_DISABLE_DMABUF_RENDERER=1` compatibility fallback. No threshold, sample floor, process scope, dependency, command authority, security boundary, or non-Linux behavior changes. Earlier measurements remain historical diagnostics but do not prove a host-startup allocator profile that the product does not ship. The tcache setting is retained only if exact-head evidence shows a meaningful RSS benefit while every launch, idle-CPU, interaction, stress, and platform gate remains green.

The exact-head `4cb52e3f863049018318ff0e2ad72c77cfb17738` tcache experiment falsified that hypothesis. The exact pinned Ubuntu/Xvfb campaign again failed only the literal frozen RSS gate at `315.590 MiB` (host `146.398 MiB`, WebKit renderer `169.191 MiB`; network `46.980 MiB` diagnostic), while cold launch (`1101.7954 ms` p95), idle CPU (`0.54817%`), renderer presence, and process-count integrity all passed. The result is statistically indistinguishable from the preceding `315.414 MiB` candidate, so `glibc.malloc.tcache_count=0` is removed completely rather than accumulated. No performance claim is taken from that failed head.

Before another allocator or renderer optimization is authorized, the next successor adds one diagnostic measurement seam only: a minimal static HTML document embedded into the same Tauri host and measured under the same pinned Ubuntu/WebKitGTK/Xvfb environment, Linux product memory profile, window geometry, descendant enumeration, settle period, and 60-second idle sampling method. The minimal binary is separately hashed and then the package is cleaned/rebuilt with the real native T143 renderer; the workflow requires the two binary hashes to differ. `platform-baseline.json` is diagnostic only: it requires a real WebKit renderer and host+renderer process accounting, but its `<=300 MiB` boolean is never propagated into T143 `all_checks_pass` and never substitutes for the product campaign. The frozen product threshold, sample floors, security/authority boundaries, dependencies, and T144 blocking semantics remain unchanged. If the same-host minimal-renderer baseline itself is at or above the frozen ceiling, that evidence must drive an explicit governance decision rather than silent threshold relaxation; if it leaves material headroom, subsequent optimization must target the measured Winds-owned delta.
